FINAL CAUSAL MODEL (confidence: high on mechanism, high on extension role)
================================================================

What the user sees
------------------
After Stanford/Duo (or a half-SSO), Outlook navigates to:
  https://login.microsoftonline.com/.../oauth2/v2.0/logout?...
That AAD page is "You're signed out of your account. It's a good idea to
close all browser windows." OWA decided the local session is unusable and
called logoutRedirect(). Auth itself succeeded.

Hard evidence: Brave vs Zen on the same afternoon (2026-09-08)
--------------------------------------------------------------
Brave success history:
  outlook.cloud.microsoft/mail/#code=<auth_code>...
  then mail loads; cookies include DefaultAnchorMailbox, msal.cache.encryption,
  ESTSAUTH session cookies, etc.

Zen failure history (repeated):
  Duo callback → outlook.*.com/mail/#  (empty hash in history) → /logout within ~1–2s
  localStorage after failure: msal.version only (0 token keys), olk-authTimings present,
  isauthed absent.

So the point of failure is post-redirect MSAL session establishment on the
Outlook origin (authorization code → tokens + session cookies), not Duo.

Why Brave "never did this"
--------------------------
Brave completed the fragment `#code=` → token exchange on outlook.cloud.microsoft.
Zen under the broken configuration did not leave a usable MSAL cache. Chromium's
cookie / Related Website Sets model is more forgiving for Microsoft's multi-host
auth; Firefox + page-mutating / request-blocking extensions make the same flow
fragile. Brave profile here has Dark Reader + Vimium but **not** uBlock.

What is NOT the root cause (falsified 2026-09-08)
-------------------------------------------------
1. OIDC cookie value '1' — present on working clean profiles too.
2. "cloud.microsoft stranded login_hint alone" — EXP-B wiped cloud.microsoft
   completely; after full Duo, still logged out (extensions still had old storage).
3. "Keeping ESTSAUTHPERSISTENT alone always fails" — EXP-H: extensions OFF,
   AAD kept, Outlook storage wiped → SUCCESS after Duo.
4. Zen engine broken — clean profile and extension-off main profile both work.
5. Missing cookie Allow / ETP exceptions — already present; necessary but not
   sufficient when extensions interfere.

What IS required for the failure we reproduced today
----------------------------------------------------
Extension interference on the SSO / OWA boot path, interacting with Firefox's
stricter partitioning and Microsoft's host migration (office.com ↔ cloud.microsoft).

Controlled results (main profile, Zen quit between mutations):

  EXP-B  wipe cloud.microsoft only; keep AAD + office.com MSAL; ext ON (old storage)
         → LOGOUT after Duo (even with clean cloud origin)

  EXP-C  wipe both Outlook storages + cache; keep AAD; ext ON (old storage)
         → LOGOUT on outlook.office.com after Duo
         (redirect_uri was office.com — host migration not required)

  EXP-D  wipe Outlook + AAD; ext ON (old storage)
         → LOGOUT after Duo (fresh AAD written during the attempt, still died)

  EXP-E  wipe Outlook + AAD; ext OFF (XPIs moved aside)
         → SUCCESS; second cold tab OK; msal tokens written

  EXP-H  wipe Outlook only; keep AAD; ext OFF
         → SUCCESS  (proves AAD keep is fine without extensions)

  EXP-G  wipe Outlook + AAD; ext ON but freshly re-enabled (old moz-extension
         storage had been deleted earlier)
         → SUCCESS

  Final  Dark Reader disabledFor SSO hosts via storage-sync; extensions ON;
         open office.com + cloud.microsoft
         → both origins isauthed with MSAL tokens; logout_count=0

Interpretation
--------------
- Old extension storage + Firefox Outlook login = failure even after AAD wipe.
- Disabling extensions (or resetting their storage) removes the failure.
- Site data / AAD wipes (--deep) still help when state is already poisoned, which
  is why zen-outlook --recover worked on 2026-09-07 — but wipes are recovery,
  not the permanent root fix.
- Prior "safe mode still failed" does not contradict this: safe mode does not
  clear poisoned OWA/AAD site data. Once poison exists, extensions are not
  needed to keep failing.

Likely extension culprits (ordered)
-----------------------------------
1. Dark Reader (dynamicTheme, enabledByDefault) — mutates DOM on login.microsoftonline.com
   / OWA boot; known to break Microsoft web apps on Firefox.
2. uBlock Origin — can block auth/telemetry/token endpoints once filter lists load.
   Brave install here has no uBlock.
3. Vimium / pdf-dark-mode — low suspicion; not isolated as necessary.

Permanent fix applied
---------------------
1. `zen-sso-harden` writes Dark Reader `disabledFor` for Microsoft + Stanford + Duo
   hosts into `storage-sync-v2.sqlite` (Zen must be closed).
2. `zen/ublock-outlook-exceptions.txt` — paste into uBlock → My filters once.
3. Keep existing `zen-sso-fix` cookie/ETP/storage-access grants + bounce-tracking
   prefs in `zen/user.js`.
4. Keep `zen-outlook --recover` (= `--deep`) as emergency recovery.

REBOOT PERSISTENCE (2026-09-11) — not Duo; local Firefox + host migration
================================================================

User report: after all prior fixes, reboot still forced private-tab Outlook
login ("You're signed out" on normal tabs). Brave never had this.

Online corroboration
--------------------
- Same Firefox/fork logout loop is widespread (Microsoft Q&A Outlook Web
  "Logging you out"; r/firefox "Solved - Outlook / M365 auto sign out" —
  ETP Custom with Cookies unchecked).
- Zen GitHub: Total Cookie Protection / Strict ETP linked to mass logouts
  (#10365); Outlook ETP exclusions alone often insufficient (#13920).
- Stanford UIT docs cover Entra device-compliance prefs on managed
  macOS/Windows browsers — not this Linux localStorage poison path.
- Duo "Remember me" cookie breakage causes *extra MFA prompts*, not the
  post-Duo AAD "You're signed out" page. Our failure is still post-Duo MSAL
  on the Outlook origin (unchanged causal model above).

Why reboot revived the bug
--------------------------
1. App-menu / reboot launches used /opt/.../zen-bin directly → skipped
   zen-sso-guard → half-auth outlook.cloud.microsoft survived.
2. uBlock My filters write crashed on Firefox IndexedDB triggers
   (`update_refcount` missing in stock sqlite3) → exceptions never stuck.
3. Dark Reader disabledFor was wiped (0 hosts) while Zen was running /
   syncing — harden only re-applied when guard actually ran.
4. TCP (cookieBehavior=5) still partitioned Microsoft's multi-host cookie
   chain; Brave does not.

Fix applied 2026-09-11
----------------------
1. `zen/user.js`: `browser.contentblocking.category=custom` +
   `network.cookie.cookieBehavior` (+ pbmode) = 0
   (accept all — same as ETP Custom with Cookies off). Category must be
   custom: Standard silently re-applies behavior 5 after user.js.
2. `bin/zen` cold-start wrapper: if no zen-bin process → zen-sso-guard,
   then exec real binary. Desktop override: `zen/zen.desktop` →
   `~/.local/share/applications/zen.desktop` (bootstrap links it).
3. `zen-sso-harden`: stub `update_refcount` so uBlock userFilters + selfie
   DELETE works; confirmed present=True after quit.
4. `zen-sso-guard --check` no longer mutates / re-runs harden.

Live state after recover+harden (2026-09-11 ~10:58):
  poisoned=none, soft grants=none, Dark Reader 16 hosts, uBlock exceptions=ok
